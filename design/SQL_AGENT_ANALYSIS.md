# วิเคราะห์แนวคิด: การเพิ่ม SQLCoder (Text-to-SQL) ผสานกับ Vector Search

เอกสารนี้วิเคราะห์ความเป็นไปได้ ข้อดี-ข้อเสีย และแนวทางการออกแบบระบบ เพื่อนำโมเดล **SQLCoder** (หรือโมเดลที่เก่งด้าน Text-to-SQL) มาใช้งานร่วมกับ **Vector Search** เดิมที่มีอยู่ เพื่อตอบโจทย์ดาน **"เวลา" (Temporal)** และ **"ข้อมูลเชิงโครงสร้าง" (Structured Data)**

## 1. ทำไม Vector Search เดิมถึงไม่พอ?
ระบบปัจจุบัน (Vector Search) เก่งมากในการหา "ความหมาย" (Semantic) แต่มีจุดอ่อนร้ายแรงคือ:
*   **ไม่รู้กาลเวลา (Time-Blind)**: Vector search หา "ความคล้าย" ของข้อความ ไม่เข้าใจว่า "วันนี้" คือวันที่เท่าไหร่ หรือ "ล่าสุด" คืออันไหน มันอาจจะดึงข้อมูลเก่าเมื่อ 5 ปีที่แล้วมาตอบถ้าเนื้อหามันคล้ายกัน
*   **นับจำนวนไม่ได้ (Counting/Aggregation)**: ถ้าถามว่า "เดือนนี้มีกี่โปรเจ็ค?", "สรุปยอดรวม...", Vector Search จะตอบไม่ได้ หรือตอบมั่ว
*   **เงื่อนไขซับซ้อน (Complex Filters)**: การบอกว่า "ขอโปรเจ็คของ User A ที่สถานะ 'Active' และแก้ไปเมื่อวาน" ยากที่จะทำด้วย Vector ล้วนๆ

## 2. แนวคิดใหม่: ระบบ Hybrid (Natural Language + SQL)

### ภาพรวมการทำงาน (Concept Flow)
การนำ SQLCoder เข้ามาจะเปลี่ยนระบบจาก RAG ธรรมดา เป็น **"Agentic RAG"** ที่มีเครื่องมือ 2 ชิ้น:

1.  **Semantic Tool (Vector Store)**: สำหรับคำถาม "คืออะไร", "ทำอย่างไร", "เนื้อหาเกี่ยวกับ..." (เหมือนเดิม)
2.  **Structured Tool (SQL Query)**: สำหรับคำถาม "เมื่อไหร่", "เท่าไหร่", "ใคร", "รายการล่าสุด"

### สถานการณ์ตัวอย่าง: "วันนี้มีโปรเจ็คไหนเข้ามาบ้าง"
*   **แบบเดิม (Vector)**: ค้นหาคำว่า "โปรเจ็ค", "วันนี้", "เข้ามา" -> อาจได้เอกสารเก่าที่มีคำเหล่านี้ แต่ไม่ใช่ข้อมูล Real-time ของวันนี้
*   **แบบใหม่ (SQL + Vector)**:
    1.  **AI Router**: จับได้ว่าถามถึง "วันนี้" (Time) และ "รายการ" (List).
    2.  **SQLCoder**: แปลงคำถามเป็น SQL:
        ```sql
        SELECT project_name, status, created_at 
        FROM projects 
        WHERE created_at >= CURRENT_DATE;
        ```
    3.  **Result**: ได้ข้อมูลตารางที่ถูกต้องแม่นยำ 100%
    4.  **Final Answer**: AI นำผลลัพธ์จาก SQL มาตอบ "วันนี้มี 3 โปรเจ็คครับ ได้แก่..."

## 3. การวิเคราะห์ความเหมาะสม (Feasibility Analysis)

| มิติการวิเคราะห์ | ผลการวิเคราะห์ | คำแนะนำ |
| :--- | :--- | :--- |
| **ความแม่นยำ (Accuracy)** | **สูงมาก** สำหรับคำถาม Time/Event | SQL คือภาษาที่แม่นยำที่สุดสำหรับการดึงข้อมูล Time-series (Logs, History, Transactions) |
| **ความยากในการทำ (Complexity)** | **ปานกลาง** | ต้องเตรียม "Schema Prompt" ให้ SQLCoder รู้จักชื่อตารางและ Column ที่ถูกต้อง ไม่งั้นจะ Query ผิด |
| **Performance** | **ดี** | SQL Query ปกติทำงานเร็วกว่า Vector Search มาก (ถ้ามี Index ที่ `created_at` หรือ `timestamp`) |
| **ความปลอดภัย (Security)** | **ต้องระวังสูง** | **ห้าม** ให้ AI รันคำสั่ง DELETE/DROP เด็ดขาด ต้องสร้าง DB User ใหม่ที่เป็น **Read-Only** เท่านั้น |

## 4. ข้อดีและข้อเสีย (Pros & Cons)

### ข้อดี (Pros)
1.  **Real-time Intelligence**: ตอบคำถามเกี่ยวกับข้อมูลปัจจุบันได้ทันที (ไม่ต้องรอ Re-index Vector)
2.  **Time Awareness**: เข้าใจคำว่า "วันนี้", "เมื่อวาน", "สัปดาห์ที่แล้ว" ได้อย่างแท้จริง ผ่าน SQL Date Functions
3.  **Reporting Capability**: สามารถตอบคำถามเชิงสถิติ (Count, Group By) ได้ ซึ่ง Vector ทำไม่ได้

### ข้อเสีย/ความเสี่ยง (Cons & Risks)
1.  **Hallucination in SQL**: โมเดลอาจเขียน SQL ผิด (เช่น จำชื่อ Column ผิด) ทำให้ Query Error -> ต้องมีระบบ Retry หรือ Error Handling ที่ดี
2.  **Schema Dependency**: ถ้าเราแก้ชื่อตารางใน DB ต้องไปแก้ Prompt ของ SQLCoder ด้วย ไม่งั้นมันจะงง
3.  **Resource**: การรัน SQLCoder อีกตัวอาจกิน Resource เพิ่ม (แต่ถ้าใช้ API หรือ Model เล็กๆ เฉพาะทางก็ไม่หนักมาก)

## 5. สรุปแนวทาง (Verdict)

**ขั้นต่อไปที่แนะนำ (Next Steps Idea):**
ไม่ต้องแก้โค้ดตอนนี้ แต่ให้เริ่มเตรียม:
1.  **Schema Context**: ลิสต์ชื่อตารางและ Column ที่สำคัญ (เช่น `users`, `projects`, `logs`, `mantis_issues`) เตรียมไว้เป็น Text
2.  **Read-Only User**: สร้าง DB User ที่มีสิทธิ์ `SELECT` อย่างเดียวเตรียมไว้

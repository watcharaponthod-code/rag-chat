# การวิเคราะห์การสตรีมและการแสดงผล Markdown

## ภาพรวม
เอกสารนี้วิเคราะห์การทำงานของระบบแชทในปัจจุบัน โดยมุ่งเน้นที่การไหลของข้อมูลจาก backend (`chat_model`) ไปยัง frontend (`chat_interface`) จุดประสงค์หลักคือระบุสาเหตุที่การแสดงผลของเนื้อหา Markdown (โดยเฉพาะระหว่างสตรีม) ไม่สอดคล้องหรือเกิดข้อผิดพลาด

## สถาปัตยกรรมการไหลของข้อมูล
1. **การสร้างข้อความ**: `llmService.js` สตรีม token จาก Ollama
2. **การส่งต่อ**: `chat.controller.js` ส่ง token ผ่าน Server‑Sent Events (SSE) ไปยัง client
3. **การรับข้อมูล**: `clientApi.ts` แยกวิเคราะห์ SSE แล้วส่งข้อความสตริงให้ `store.ts`
4. **การอัปเดตสถานะ**: `store.ts` เพิ่มเนื้อหาใหม่ให้กับข้อความและทำให้ React รีเรนเดอร์
5. **การแสดงผล**: `ChatInterface.tsx` ประมวลผลสตริงและใช้ `ReactMarkdown` แสดงผล

## พบปัญหาที่สำคัญ (วิเคราะห์บรรทัดต่อบรรทัด)

### 1. ปัญหา "ลิงก์หายไป"
**ตำแหน่ง**: `ChatInterface.tsx` บรรทัด 297
**โค้ด**: `.replace(/(?<!\!)\[[^\](]+\](?!\[|\()/g, '')`
**วัตถุประสงค์**: ลบ citation เช่น `[Document Name]` แต่คงลิงก์ `[ข้อความ](URL)` ไว้
**ข้อผิดพลาด**:
-   ในระหว่างสตรีม ลิงก์มาถึงเป็นชิ้นส่วน เช่น `[คลิกที่นี่]` (ยังไม่มี `(URL)`)
-   Regex ตรวจสอบว่าไม่มี `(` หรือ `[` ถัดไป จึงถือว่าเป็น citation และ **ลบออก**
-   เมื่อชิ้นต่อมาถึงคือ `(https://example.com)` เราจะเหลือแค่ URL โดยไม่มีข้อความ ทำให้ลิงก์หายและแสดงผลผิดพลาด
-   ผลลัพธ์: ข้อความลิงก์หายไปอย่างถาวร ทำให้ UI กระตุกและผู้ใช้สับสน

### 2. ปัญหา "ทำลายการเยื้องโค้ด"
**ตำแหน่ง**: `ChatInterface.tsx` บรรทัด 298
**โค้ด**: `.replace(/  +/g, ' ')`
**วัตถุประสงค์**: ทำความสะอาดช่องว่างหลายช่องให้เป็นช่องเดียว
**ข้อผิดพลาด**:
-   โค้ดหลายภาษาต้องอาศัยการเยื้อง (เช่น Python 4 spaces) ซึ่งถูกลดเหลือ 1 space ทำให้โค้ดเสียโครงสร้าง
-   ใน Markdown การใส่สองช่องว่างท้ายบรรทัดหมายถึง "hard break" การลบช่องว่างทำให้บรรทัดต่อเนื่องกันโดยไม่มีการขึ้นบรรทัดใหม่
-   ส่งผลให้โค้ดแสดงเป็นบรรทัดเดียวและอ่านยาก

### 3. ปัญหา "การแทนที่รูปภาพช้าและกระตุก"
**ตำแหน่ง**: `ChatInterface.tsx` บรรทัด 293 (`injectImageReferences`)
**วัตถุประสงค์**: แทนที่ `[Figure X]` ด้วยลิงก์รูปภาพ
**ข้อผิดพลาด**:
-   ฟังก์ชันนี้ทำงานทุกครั้งที่มี token ใหม่ (อาจหลายพันครั้งต่อการตอบ) ทำให้ทำงาน O(N²) และใช้ CPU มาก
-   หาก `[Figure 1]` ปรากฏในโค้ดบล็อกหรือ inline code การแทนที่แบบสตริงจะทำลายโค้ดนั้นด้วย
-   ทำให้ UI กระตุกและประสบการณ์ผู้ใช้แย่ลง

### 4. ปัญหา "การรีเรนเดอร์กระตุก"
**สังเกต**: เนื่องจาก `processedContent` แก้ไขข้อความโดยใช้ regex ที่อิงกับ **ข้อความทั้งหมด** การเปลี่ยนแปลงโครงสร้าง Markdown (AST) ระหว่างเฟรมทำให้ส่วนต่าง ๆ ปรากฏ/หาย/ย้ายตำแหน่งอย่างต่อเนื่อง (เช่น ลิงก์หายแล้วกลับมา) ทำให้ UI กระพริบและสับสน

## แนวทางแก้ไขที่เสนอ (วิธี "ถูกต้อง")

### หลักการสำคัญ
**ห้าม** แก้ไขสตริง Markdown ด้วย `String.replace()` เพื่อทำ formatting ใด ๆ ควรใช้ **Remark plugins** หรือ **component mapper** ของ `ReactMarkdown` เพื่อจัดการที่ระดับ AST เท่านั้น

### ขั้นตอนปฏิบัติ
1. **ลบการประมวลผล regex** จาก `ChatInterface.tsx` (บรรทัด 292‑304) ให้ส่ง `message.content` ดิบตรง ๆ ไปยัง `ReactMarkdown`
2. **สร้าง Remark Plugin** สำหรับการซ่อน citation
   -   Plugin จะเดินทางใน AST แล้วลบ node ที่เป็น `[[]]` หรือรูปแบบ citation ที่ต้องการ
   -   ทำงานเมื่อ Markdown ถูกพาร์ส ดังนั้นข้อความที่ยังไม่สมบูรณ์ (เช่น `[Link]` ยังไม่มี URL) จะยังคงเป็น text จนกระทั่งครบ
3. **จัดการรูปภาพด้วย Component**
   -   สร้าง component เฉพาะสำหรับ pattern `[Figure X]` ที่แปลงเป็นปุ่มหรือไอคอนคลิกได้
   -   ทำใน `components` ของ `ReactMarkdown` แทนการ `replace`
4. **ปรับปรุงประสิทธิภาพ**
   -   เนื่องจากไม่มีการประมวลผลสตริงซ้ำ ๆ การอัปเดต UI จะเร็วขึ้นและไม่มี jitter
5. **ทดสอบ**
   -   ตรวจสอบการสตรีมข้อความที่มีลิงก์, code block, citation, และรูปภาพหลายรูป
   -   ยืนยันว่าไม่มีข้อความหาย, โค้ดเยื้องถูกต้อง, ลิงก์แสดงครบถ้วน

## สรุป
การแก้ไขโดย **ยกเลิกการใช้ regex** และ **ใช้ Remark plugin + component mapper** จะทำให้การแสดงผล Markdown สอดคล้องกันตลอดการสตรีม ลดการกระตุกของ UI และรักษาโครงสร้างโค้ด/ลิงก์/รูปภาพอย่างถูกต้อง
